# 发布后维护

本说明用于处理已发布版本的真实反馈。用户可通过[问题反馈表单](https://github.com/Polarzen/net-monitor/issues/new?template=bug_report.yml)或[空白 Issue 入口](https://github.com/Polarzen/net-monitor/issues/new/choose)报告问题；填写前参阅 [README 常见问题与隐私提示](../README.md#常见问题)。各版本的运行证据和验证缺口统一见 README 链接的对应发布记录，不在此复制历史验收。

从 GitHub 获取产品后的正常使用和失败结果均可提交[下载后的使用反馈](https://github.com/Polarzen/net-monitor/issues/new?template=release_feedback.yml)。维护者先确认包身份、实际获取方式和环境，再按用户实际操作逐项记录；“暂未发现问题”不是全部项目通过，没有 Issue 或有下载次数也不是运行成功证据。转交包、测试光盘和源码运行的结果保留其各自来源，不能改记为 GitHub 直接下载验收。

## 反馈分类

按证据区分五类：已复现的产品缺陷、需要更多证据的问题、使用或环境问题、尚未覆盖的验证范围、可选功能建议。记录观察到的现象、涉及版本和证据来源，并把推测与事实分开。报告者不必先证明根因；偶发问题可先保留当时的操作与频率，再询问解决疑点所需的最少信息。

“未验证”不等于“已知故障”。工具无法定位管理员窗口，也不能直接认定产品有缺陷。使用或环境问题应有具体依据，例如只复制 EXE 后缺少依赖；不能将未知原因一律归咎于用户环境。检查是否已有相同版本、相同现象的报告，有依据时关联已有记录，不因描述相似就自动关闭问题。没有真实反馈时，不创建样例故障，也不为每项未验证行为新建 bug。

## 处理顺序

优先处理无法启动、正确权限下无法基本采集、崩溃、明显错误归属、数据异常或无法退出。其次处理影响正常阅读、操作或配置保存的可复现问题。纯审美调整、新统计、新图表、自动更新及其他功能建议暂不主动扩展。

这是轻量维护顺序，不代表响应时限、服务等级或修复承诺。需要补充信息时，说明尚缺哪项事实及其用途，不要求公开整个诊断包、私人配置或完整进程列表；截图和错误原文先检查隐私。不把临时绕过安全保护作为排障方案，也不把自动测试结果等同于全部实机验证。

## 最小修改流程

实际反馈 → 核对版本与环境 → 最小复现 → 最小修复 → 对应回归 → 必要的 EXE 复验 → 新版本发布。无法稳定复现时记录证据和未知项，不预填“已复现”或“已修复”。后续版本范围依据已确认的问题或用户明确授权确定；反馈分类本身不自动产生新版本。

涉及采集正确性时保留原始数值、采样时序及必要的进程身份信息；公开内容应去除敏感标识，原始证据仍供核对。不能修改计数器迎合预期、削弱身份检查或将未知显示为零。修复应有针对性回归；影响打包、启动、提权或采集时，对最终候选 EXE 做必要复验，不自动重开整套历史验收。先审阅明确的 PR 提交，再按仓库规则合并，不绕过检查。

## 发布资产保持不变

已公开发布的版本标签、产品 ZIP 和校验文件保持不变。产品修复使用新的版本与标签，不把新二进制覆盖到旧版本名下。每份发布包的源码提交、构建来源、哈希与实际运行证据必须能对应。

文档合并后 CI 自动生成的包只是该提交的构建检查结果，不替换已发布包，也不自动继承旧包全部运行结论。纯反馈入口或文档维护不递增产品版本、不触发人工桌面补验；既有软件继续使用，后续按真实问题处理。
